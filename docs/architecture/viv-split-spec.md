## 2. 辩证讨论

### 2.1 拆还是不拆

**反方（维持单文件）**：
- 教训 1/5 的直接推论——fluent 重写（27 文件 +3,347）引发回滚；拆 21k 行 = 更大的结构变更；
- 上游 voidtools 就是单文件风格，拆分增加未来 merge 上游的成本；
- C 编译器对单编译单元的静态检查最严（跨文件调用必须走头文件声明，反而丢失隐式一致性）；
- 每轮 bug 修复（R63–R67）虽都在 viv.c，但都修完了——现状"能工作"。

**正方（拆）**：
- 教训的实质是"单轮变更量失控"，不是"文件应该大"——fluent 是**重写行为**，本方案是**纯物理移动**（函数体逐字节不变），风险模型完全不同；
- fork 与上游已深度分叉（b41/b42/rc.1/rc.2 + 回滚史），"保持上游形状"的收益已趋零——上游 merge 本就不现实；
- 守卫测试按 `viv.count(...)` 形态匹配巨型文件，域越混守卫越写不准（R64/R67 守卫演进已在挣扎）；
- 21k 行里任何导航/评审/冲突面都在放大后续每一轮的边际成本。

**裁决：拆**，但以"纯移动 + 状态层先行 + 域封闭性升序"把 fluent 式风险（行为重写）从物理上排除。

### 2.2 按什么维度拆

- **方案 A（按技术层级：ui/render/core）**：违反 writing-plans 的"按职责拆分，而非按技术层级"——把高内聚职责链（如 webp 动画的加载+定时器+渲染）撕碎到三层。否决。
- **方案 B（按功能域）**：每域一起变更、一起被守卫锁定、与仓库既有模块模式（config.c/os.c/string.c 职责单一、各配 .h）一致。**采纳**。
- **方案 C（最小拆分：只抽三巨头）**：WndProc 分发/加载线程/options 对话框。治标——viv.c 仍 ~16k 行。作为 B 的阶段产物吸收（三巨头分别落在终片/加载片/对话框片）。

### 2.3 共享状态怎么办（本设计的核心）

测量事实：159 个文件级 static 被全域共享；`_viv_hwnd` 被六个候选域引用 220–238 次；
playlist 域的 6 个 static 全部被域外直接访问——**viv.c 不是"函数太长"，是"共享上下文 + 域逻辑绞合"**。

- **方案 A（访问器封装）**：每个搬走的 static 配 getter/setter。边界最干净，但每片引入新代码（访问器）+ 调用点改名，diff 面扩散到消费端——违背纯移动纪律，风险回归 fluent 模式。否决（域成熟后可再逐个收回，见 §4 终态）。
- **方案 B（extern 状态层）**：159 个 static 集中为 `viv_state.h` 的 extern 声明（定义仍在 viv.c），各新域 include。C 消息驱动架构（GDI/Win32）状态天然共享，extern 是该生态的惯例（os.c 的 `os_GdiplusToken` 同模式）；每片 diff = 纯移动 + 一行 include；编译器对 extern 的类型检查完整保留。**采纳为过渡态**。

### 2.4 守卫兼容（拆分的隐藏成本）

menu_structure_test.py 有 125 处 `viv.c` 引用、zoom_math 16 处、simulation 2 处。
拆分后这些守卫若逐条改读新文件 = 巨型测试 diff 且每片重复付费。

**策略：read 拼接**——三套件的读取助手改为"viv.c + 所有 `src/viv_*.c` 按字典序拼接"。
纯移动保证总文本不变 → 现有 125+16+2 处守卫**零修改自动继续全绿**，
新域文件自动纳入守卫视野。每片的测试 diff 恒为一行（首次引入拼接助手时）。

### 2.5 命名与目录

- 新模块命名 `viv_<domain>.c/.h`（`viv_recent.c`、`viv_playlist.c`……）：与既有通用模块（os/string/mem——无 viv 前缀）区分"应用域模块"层级，且杜绝与上游未来文件名冲突；
- 目录留在 `src/`（不建子目录——vs2019/vs2026/nsis 全部按 `src\*.c` 扁平约定，props 单点加行即可双工程生效，已验证两工程均 import `voidImageViewer.files.props`）。

## 3. 决策摘要

1. **片 0 = 状态层先行**：新建 `src/viv_state.h`（159 个 extern 声明，分组注释），viv.c 定义保持不动仅去 static。编译器全量验证、零行为变化。此片独立成轮，因为它本身 ~200 行 diff。
2. **域片按封闭性升序**（测量驱动，见 §4 片序表）：状态共享越少越先拆，每片积累"域文件已存在"的势能，最后拆高耦合域时消费端已就位。
3. **纯移动纪律**：每片只允许 ①剪切函数 ②粘贴到新 .c ③新 .h 声明导出面 ④props 加编译单元 ⑤守卫拼接自动覆盖 ⑥Changes.txt 记录移动清单。**禁止**任何函数体重写/重命名/重排序。
4. **viv.c 终态**：残余 = `_viv_proc` 分发 + init/kill + 命令分发 + 状态定义，目标 <5,000 行（后续再评估是否拆 WndProc）。
5. **每片门禁**：G1 三套件（拼接后自动绿）+ G2 编译零警告（CI 双工具链 windows-2022 v143 + windows-2025 v145）+ G3 push 触发 CI + G4 用户实机冒烟（拆分轮合并验收节奏：每 2–3 片一次实机，纯移动风险递减）。
6. **回滚**：每片一个 commit，出问题 `git revert` 单片；任何时点上一 release tag 恒可回滚（流程 4）。

## 5. 风险登记

| 风险 | 缓解 |
|---|---|
| extern 化引入隐式跨单元耦合 | 过渡态设计（§4 终态后逐域收回私有化）；守卫拼接恒全量扫描 |
| 纯移动中遗漏前置声明 | 编译器硬门（G2/CI 双工具链 0 error 0 warning） |
| 守卫拼接顺序敏感 | 拼接按字典序 + 纯移动保证文本不变；拼接助手本身加守卫（round69） |
| CI image 漂移（MSB8020 类） | 已 pin windows-2022 + windows-2025 双腿（tests.yml 现状） |
| 用户验收节奏被拆分潮淹没 | 拆分轮合并验收：每 2–3 片一次实机；rc 转正决策不受拆分影响（用户指令触发） |
